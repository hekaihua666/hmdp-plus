## 四、P1：先设计订单状态与可靠交接

### 1. 把申请状态与订单状态分开

- 申请状态表达“请求是否受理、是否已生成订单、是否失败或正在补偿”。
- 订单状态第一版限定为“待支付、已支付、已关闭”；暂不展开退款和售后。
- 超时未完成的申请先进入待核查，不能仅凭等待时间就恢复库存。
- `orderId` 用于追踪一次申请，消息另外有 `eventId`；重发消息沿用同一业务标识。
- 增加申请结果查询和订单查询，校验当前用户归属；接口返回“已受理”不能写成“落单成功”。

拟新增持久化申请记录，至少包含订单 ID、用户、优惠券、受理结果、处理状态、错误原因和时间。具体表结构在本阶段固定，不先写一套通用任务平台。

### 2. 数据库兜底与业务规则

1. 核实、清理已有重复记录后，再增加或确认用户与优惠券唯一索引；禁止盲目对运行库执行变更。
2. 同一订单重放，返回既有处理结果，不重复扣库存。
3. 不同订单 ID 命中同一用户与优惠券时，作为业务冲突处理，不能冒充该申请落单成功。
4. MySQL 扣库存、插入订单和更新申请成功状态放在同一事务中；ES、Redis 副作用不能借此宣称一起回滚。
5. 第一版约定：成功落单后，即使订单超时关闭，也保留该用户本场活动的购买记录；落单前申请最终失败，才按规则释放本次购买资格。后续若允许重新购买，必须重新设计唯一约束，不能只删除 Redis 标记。

### 3. 可靠生产：事务消息为首选候选，必须通过设计关卡

目标是用 RocketMQ 替换核心 Stream 队列。不能只是删 `XADD`，然后在 Lua 返回后发送普通消息：Redis 预占与 MQ 发送之间存在崩溃窗口。

首选评估流程：

```text
基础鉴权、时间和参数校验
    → 发送半消息
    → Lua 幂等校验并预占，记录本次预占身份与结果
    → 持久化申请裁决结果
    → 提交 / 回滚消息；结果不明确则等待回查
    → 消费者事务落单
```

该流程是候选设计，不代表仅按箭头实现就可靠。编码前要用故障窗口表回答以下问题：

| 故障窗口 | 必须明确的处理 |
| --- | --- |
| 半消息发送失败或结果不确定 | 不盲目再次扣库存；同一申请可识别、可查询 |
| Redis 预占成功，申请记录未提交就崩溃 | 能定位本次预占，并恢复裁决或幂等补偿 |
| 申请记录成功，消息提交结果未知 | 回查使用可靠申请结果，不依赖进程内变量 |
| Redis / MySQL 暂时不可读 | 查询失败不是业务失败，也不是“未预占”；避免错误提交或回滚 |
| 回查确认失败时，本地执行还未结束 | 有终态裁决和并发控制，防止已经失败后又预占 / 落单 |
| 回查耗尽、消息回滚，但库存已预占 | 对账发现并恢复孤立预占；MQ 回滚不会自动撤销 Redis |
| Redis 重启或数据丢失 | 明确持久化、恢复和库存重建规则，不能简单用数据库库存覆盖存在待处理申请的库存 |

事务消息并不把 Redis、MQ、MySQL 组成一个原子事务。预占标识应绑定本次订单，终态裁决后旧消费者不能再次落单。实现前固定裁决依据、超时、数据保留期和故障恢复规则。

如果上述问题无法在可维护范围内闭合，先调整为“数据库受理记录 / 库存约束 + 可靠发布”的方案，并明确请求路径增加数据库写入的成本；不要同时实现两套生产机制，也不要为展示事务消息跳过一致性问题。

## 五、P2：迁移 RocketMQ 异步下单，完成恢复闭环

### 1. 改哪些位置

| 当前位置 | 改造职责 |
| --- | --- |
| `VoucherOrderServiceImpl.seckillVoucher` | 受理申请，调用可靠生产流程，返回申请 ID |
| `seckill.lua` | 去掉最终 Stream 入队，保留校验与幂等预占；增加本次预占识别和对应补偿脚本 |
| `VoucherOrderHandler` | 验收通过后移除，用 MQ 消费者接替；同一申请不能由两条链路同时扣库存 |
| `createVoucherOrder` | 拆为清晰的事务落单服务，处理重复、业务冲突及申请终态 |
| `VoucherOrderController` | 增加申请和订单查询；关键步骤解释“受理”与“创建”的区别 |
| 拟新增 `mq` / `job` 模块 | 放生产、回查、消费、补偿、对账职责，不做跨项目通用消息框架 |

业务逻辑放在服务层；生产者、消费者只负责消息交接。关键代码写完整注释，说明为什么这样确认、重试、裁决或补偿。

### 2. 消费与补偿规则

- 消费成功：数据库事务提交后再确认消息。
- 暂时失败：数据库不可用等问题进入有限重试；具体返回失败的方式按所选 SDK 确认，不能吞异常后正常返回。
- 永久失败：记录原因，进入明确终态和补偿；重复消息不应无限重试。
- 死信处理：记录事件、申请、原因和处理人；支持显式重新投递或终止，不做匿名开放的重放 HTTP 接口。
- 并发控制：消费者落单与补偿通过持久申请状态协调。数据库条件更新或锁保证终态互斥，不能补偿完成后旧消息又创建订单。
- 库存补偿：按订单 ID 确认本次预占、确认未补偿后再恢复；不能简单“加一并删用户标记”。
- Redisson：先核对现有锁的作用，数据库唯一约束保留；不能因为用了 MQ 就宣称不再需要并发控制。
- 对账：比较申请、订单、数据库库存和 Redis 预占；存在处理中申请时不能要求 Redis 与数据库库存时时相等。

### 3. 必做故障验证

1. 同一申请重复提交、同一消息重复投递。
2. 多人抢同一张券，最终无重复订单、无数据库负库存。
3. 半消息、Redis 预占、申请记录、消息提交之间分别中断进程。
4. 消费者在数据库提交前、提交后确认前分别重启。
5. 暂停数据库，恢复后订单继续处理；永久失败消息进入可处理的异常路径。
6. 重试、补偿与旧消息重放并发时，只出现一个终态，库存不重复恢复。
7. 两个消费者实例共同处理消息，结果仍正确。

- [ ] 每个故障场景保存操作、期望、实际结果和库存核对；压测前先通过正确性验证。

## 六、P3：延迟消息关闭超时订单

### 怎么干

1. 增加 `pay_deadline` 或等价持久截止时间；订单创建事务同时写待发送到期检查事件，避免创建成功却未安排检查。
2. 发送任务按所选 RocketMQ 版本安排延迟 / 定时消息；配置不混用 4.x 延迟等级和 5.x 投递时间语义。
3. 消费者查询数据库，仅对“到期且待支付”订单执行关闭。提前到达时重新安排检查，已支付或已关闭时幂等结束。
4. 通过数据库条件更新裁决“模拟支付”与“超时关闭”，第一版只做本地模拟支付，不接真实支付平台。
5. 关闭状态、恢复数据库库存、写 Redis 补偿任务放在同一 MySQL 事务中；Redis 失败由持久任务继续处理。
6. 定时扫描过期待支付订单作为兜底；消息是触发器，数据库截止时间和状态是依据。

### 验收与产物

- [ ] 重复到期消息不会重复恢复库存。
- [ ] 支付与关闭竞争时，只能一个状态流转成功；已支付订单不释放库存。
- [ ] 应用重启、到期消息发送失败、Redis 补偿失败后均有恢复路径。
- [ ] 记录本场活动禁止再次购买的规则与申请结果查询表现。
- [ ] 形成 `docs/order-state-and-timeout.md`。

## 七、P4：Outbox + MQ 可靠同步商户 ES

### 怎么干

1. 在 `ShopServiceImpl.saveShop/update` 的数据库事务中，同时写商户变更事件。
2. 保留提交后的Redis详情缓存失效处理；Redis GEO已在轻社交精简阶段退役。后续若改ES持久同步，不顺带扩大Redis治理范围。
3. 发送任务确认 Broker 收到后标记发送成功；确认不明允许重发。多实例运行前增加事件领取与过期恢复机制。
4. 消费者读 MySQL 最新完整商户，以 `shopId` 更新 ES；持久商户版本随修改递增，写 ES 时防止旧版本覆盖。
5. 使用本次查询得到的数据及版本，不能把旧事件版本套在最新数据上。若以 ES 外部版本实现，先验证客户端与冲突处理行为。
6. 消费失败进入重试、异常记录及显式重放。待发送事件“已发送”不能冒充“ES 已同步”。
7. 可用一张小型待发送事件表承载商户同步与到期检查，按事件类型分派；不要提前抽象通用事件平台。

### 验收与产物

- [ ] 商户事务回滚，事件也回滚；MQ 停机期间已提交事件可在恢复后补发。
- [ ] 发送成功但标记前崩溃，重复投递仍正确。
- [ ] ES 停机后恢复可补同步；同一商户连续更新不留下旧版本。
- [ ] 原搜索、补全、筛选和详情入口回归通过；当前无删除业务，不新增无关删除流程。
- [ ] 形成 `docs/shop-sync-verification.md`，解释最终一致性及同步延迟。

## 八、P5：缓存、部署、压测与简历收尾

### 1. 缓存按问题选择

- 先测普通详情查询和热点到期时数据库回源，不把工具类中存在的方案写成实际启用。

- 记录优化前后环境和负载，验证收益后再扩大使用范围。

### 2. Docker / Linux 交付

- 写项目 Dockerfile、Compose、配置示例、健康检查、日志与数据卷说明；ES 插件和索引初始化单独说明。

- 区分普通测试、真实依赖集成测试和会修改索引的维护操作；危险维护命令显式启用。

### 3. 日志与性能证据

- 日志关联 `traceId`、`orderId`、`eventId` 与 Broker 消息 ID，记录发送、消费、重试、补偿与死信。
- 观察消息积压、最老未完成申请时长、失败数、重复消费和补偿数；按测量结果设置入口限流。
- 分别压测：详情缓存、ES 搜索、秒杀受理与实际落单。记录数据规模、环境、预热、并发、请求量、吞吐、P95/P99、错误率。
- 秒杀同时统计业务拒绝、技术失败、受理成功和最终订单完成；不能只测受理接口就宣称下单性能提升。
- 记录消息积压消退时间和库存核对结果；保留脚本及原始报告，不编造百分比。
- 从请求入口到恢复机制讲解一次，并保存一次真实故障排查过程。没有诊断需求时，不增加一整套监控平台。

## 九、范围控制：做深核心，不扩张业务

- ES 保持商户搜索范围，不恢复无实际用途的用户、笔记搜索。
- MQ 聚焦下单、超时关单、商户同步，不新造积分、推送、风控等多个系统。
- 重试、幂等、死信与补偿为必做配套；顺序消息、广播、批量发送按真实需求再引入。
- 暂不做真实支付、退款、售后、微服务拆分、Kubernetes、多机房和 Broker 内核研究。
- 一个业务工程即可承载第一版，按职责组织服务与消息代码。必要复杂度服务可靠性，避免通用平台抽象。

## 十、接下来马上做的四件事

## 十一、官方资料与使用边界

- [RocketMQ 事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)：半消息与回查协调消息生产和本地结果，不能替代消费幂等及库存补偿。
- [RocketMQ 消费重试](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)：暂时故障、有限重试和死信处理；具体行为按选定客户端与消费模式核实。
- [RocketMQ 延迟消息](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/)：到期触发检查，业务截止时间仍保存于数据库。

上述官方页面为 RocketMQ 5.0 文档入口，解释能力边界；实际落地必须按固定 Broker / SDK 版本核对配置和调用方法。
