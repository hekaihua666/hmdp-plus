# Redis Stream 迁移 RocketMQ 代码复查

审查日期：2026-10-26。审查对象为当前本地工作区，HEAD 为 `34d3dcf`，包含原有未提交改动。本轮未修改业务源码、数据库结构或运行中的业务数据。

## 结论

方案方向合理：申请表承担持久化受理与待发布记录，Redis 承担幂等预占，MQ 承担异步传递，数据库事务完成落单，恢复任务负责补发和补偿。它没有同时维护两套业务消息队列，也没有另建重复的消息表。

目前最值得处理的是一个补偿完成判定缺口，以及 HTTP 路径中的数据库访问与重复写入。保留状态机和数据库唯一约束，做一次有针对性的收敛即可；无需更换 MQ 或重写整个方案。

## 发现与建议

### F1 / P1：预占凭据同时丢失时，补偿会被错误判定为完成

- 位置：`src/main/resources/seckill-release.lua:25`、`:40`；`src/main/java/com/hmdp/mq/SeckillRecovery.java:93`。
- 触发条件：申请已经预占，Redis 库存仍保留扣减结果，但本申请的 HELD 标记与 owners 归属同时丢失，例如误删或部分键丢失。这不是正常抢购路径。
- 当前脚本在两项凭据均不存在时，跳过归还库存，直接写 CLOSED 并返回 0。Java 随后将 CANCELLING 更新为 FAILED，恢复扫描不再处理它。
- 结果：订单未创建，可售库存少一份，而且申请已经退出自动补偿流程。
- 隔离复现：初始 stock=1；执行原始预占脚本后 stock=0；删除 owners、marker；执行原始释放脚本，得到 `release_code=0, stock=0, marker=CLOSED`。正常对照场景会恢复到 stock=1，重复释放保持为 1。
- 建议：保留能够区分“确认预占、确认未预占、预占结果未知”的持久化信息。对确认预占或结果未知而凭据不全的申请，保留补偿/核查状态；只有明确无需归还，或幂等释放成功，才进入 FAILED。不要直接在凭据缺失时无条件加库存，也不要给所有无凭据情况一律返回成功。
- 验证方法：新增对应 Lua 与状态机回归，断言该异常场景不会进入 FAILED；恢复证据后可以继续收敛。

### F2 / P2：正常 HTTP 受理路径承担 11 次数据库访问，并同步等待 MQ 发送

- 位置：`src/main/java/com/hmdp/service/impl/VoucherOrderServiceImpl.java:64`、`src/main/java/com/hmdp/mq/SeckillRecovery.java:74`、`src/main/java/com/hmdp/mq/SeckillOrderPublisher.java:67`。
- 条件：券有效、Redis 库存已初始化、预占成功、MQ 返回 SEND_OK；仅统计 HTTP 路径，不包含消费者落单和事务提交本身。
- 用实际入口、状态机、恢复器和发布器，替换外部依赖后得到以下调用计数：

| 操作 | 次数 |
| --- | ---: |
| 查询优惠券 | 2 |
| INSERT 申请 | 1 |
| selectById 查询申请 | 4 |
| FOR UPDATE 查询申请 | 1 |
| 更新 READY | 1 |
| claimSend 领取发送租期 | 1 |
| sent 更新发送结果 | 1 |
| 合计 | 11 |

- `syncSend` 仍由 HTTP 线程调用，默认发送超时配置为 3000ms。因此“订单落库异步”成立，“HTTP 完全不等 MQ”不成立。
- 库存不足和重复请求也先查券、插申请，再进入 Lua 判断。这是当前可靠受理方案的成本，MQ 只将最终落单移出请求线程，没有隔离所有请求对数据库的压力。
- 建议优先合并推进过程中的重复普通读取，保留用于并发裁决的行锁查询和 claimSend。若目标是更快受理，可在申请持久化后交给受控后台发布；若目标包含高并发，再加入无副作用的售罄/重复预检或限流。正式预占仍必须有持久化受理依据，避免重新打开悬空预占窗口。
- 本项为调用成本测量，并非真实吞吐量或响应时间压测。

### F3 / P2：预占业务失败时重复 UPDATE 同一条申请

- 位置：`src/main/java/com/hmdp/service/SeckillRequestService.java:193`、`:198`、`:219`。
- `prepare()` 的失败分支先调用 `cancelling()`，该方法已经执行 updateById；返回后 `prepare()` 再执行一次 updateById。
- 使用实际 `prepare()` 隔离复现，Lua 返回码 1、2、3、4 均产生两次更新，最终状态都是 CANCELLING。
- 建议：失败分支调用 cancelling 后直接 return，成功分支单独更新 READY。保持现有事务和行锁不变即可去掉一次写入。
- 验证方法：四种返回码各断言只更新一次，且失败原因和状态不变。

### F4 / P2：用户级 Redisson 锁扩大争用，且释放早于事务提交

- 位置：`src/main/java/com/hmdp/service/SeckillRequestService.java:286`、`:319`。
- `lock:order:{userId}` 让同一用户购买不同券也互斥；tryLock 失败会抛异常触发消息重试，这类不同券操作可以互相拖延。
- 锁在事务目标方法的 finally 中释放，Spring 随后才提交事务。因此它并没有覆盖到数据库提交完成；当前正确性仍有申请行锁、Lua 归属和数据库唯一约束支撑。
- 建议先确认业务是否要求“同一用户所有券订单都串行”。若只要求一人一券，评估将锁细化到用户与券，或在覆盖并发场景后移除冗余锁。若保留锁并要求覆盖提交，必须把锁放在事务代理调用外层，或在事务完成后释放。
- 这项主要是锁职责与额外重试问题，不将它单独定性为已发生重复订单。
- Spring 5.3.23 的提交顺序可核对 [TransactionAspectSupport](https://github.com/spring-projects/spring-framework/blob/v5.3.23/spring-tx/src/main/java/org/springframework/transaction/interceptor/TransactionAspectSupport.java)。

### F5 / P2：恢复任务串行发送，慢发送会拖住后续补偿

- 位置：`src/main/java/com/hmdp/mq/SeckillRecovery.java:46`、`:48`、`:82`。
- 一轮最多取 20 条，逐条 advance；READY 分支同步发 MQ，补偿分支也在同一循环中。
- fixedDelay=1000 的含义是“本轮执行结束后再等 1 秒”，不是每秒必定处理 20 条。若 20 次发送都耗时约 3 秒，单轮发送时间约 60 秒，这是配置推算，不是本机实测。
- 现有异常隔离只解决抛异常后的继续执行，无法解决单条请求等待很久时其余申请被阻塞。
- 建议限制每轮处理耗时，或让发送与补偿有各自受控的执行能力。继续复用 claimSend 和幂等逻辑；不要改成无限线程或无界异步提交。

### F6 / P2：申请记录与 Redis 终态标记持续累积

- 位置：`src/main/java/com/hmdp/service/SeckillRequestService.java:141`、`src/main/resources/seckill-release.lua:43`、`src/main/resources/seckill-reserve.lua:76`。
- 每次受理都会插入新申请；失败申请也会生成 CLOSED 标记。相关键无 TTL，申请表无归档清理流程。重复点击、售罄请求同样扩大数据量。
- 长期保留处理中申请的幂等依据是必要的；所有终态永久保留则会增加内存、索引和查询成本。
- 建议明确终态保留期、消息重放窗口和活动结束后的归档策略，分批清理已经终态且越过安全窗口的数据。处理中记录和有效购买资格不能随意删除。

### F7 / P2，静态性能风险：恢复 SQL 的筛选、排序与索引不完全匹配

- 位置：`src/main/java/com/hmdp/mapper/SeckillRequestMapper.java:59`；`database/migrations/20261016-seckill-mq.sql:15`。
- SQL 同时按 state/next_send_time/deadline 做 OR 筛选，再按 update_time/order_id 排序。现有恢复索引只有 `(state,next_send_time)`，不覆盖 deadline 分支和排序。
- LIMIT 20 限制的是返回条数，不等于数据库最多检查 20 行；在终态记录持续累积时，这条每轮执行的查询值得优先看执行计划。
- 本轮尝试只读 EXPLAIN，但工程配置的 MySQL 连接被拒绝。因此没有把全表扫描或具体耗时写成已验证结论。
- 建议在实际数据规模下 EXPLAIN，根据结果统一扫描顺序与索引，必要时拆分不同到期条件；不要盲目增加多个索引。

### F8 / P2：异常日志丢失根因，死信失败路径缺少明确处理说明

- 位置：`src/main/java/com/hmdp/service/impl/VoucherOrderServiceImpl.java:73`、`src/main/java/com/hmdp/mq/SeckillOrderPublisher.java:85`、`src/main/java/com/hmdp/mq/SeckillRecovery.java:53`。
- 库存初始化失败直接返回通用提示且不记异常；发送与恢复日志主要记录异常类名，嵌套异常的原因和调用位置被丢弃，多个根因会显示成同一种 IllegalStateException/MessagingException。
- 对前端保持简洁提示是合适的；内部日志应保留 orderId、操作阶段与经过脱敏的异常根因，必要时记录堆栈。对重复故障可限频，避免循环刷屏。
- 死信处理器同样配置 maxReconsumeTimes=3。抛异常会触发该处理消费组自己的重试/死信路径，并非始终停留在原业务 DLQ。“留在原 DLQ 等人工处理”的注释不准确，应明确最终异常消息去向和核查入口。
- 经典客户端转发失败消息可核对 [RocketMQ 5.3.2 SendMessageProcessor](https://github.com/apache/rocketmq/blob/rocketmq-all-5.3.2/broker/src/main/java/org/apache/rocketmq/broker/processor/SendMessageProcessor.java)。本项路由机制由 SDK/Broker 源码核对，本轮未重跑 Broker 联调。

### F9 / P3：注释与代码规范有几处明显不一致

- `SeckillRequest.java:14` 将旧 Stream 描述为进程崩溃后请求会消失。基线代码的 Lua 已有 XADD，消费者已有 pending-list 处理；新方案的价值应解释为持久状态协调、结果查询、补发和补偿，而不是把进程崩溃直接等同消息消失。
- `VoucherOrderServiceImpl.java:28` 将旧版称为同步下单，但本次替换的旧实现已经通过 Stream 异步落单。
- 多处将 RedisIdWorker 生成的 ID 称作雪花 ID；实际实现是时间戳加 Redis INCR 序列。
- `SeckillRequestMapper.java:13` 声称所有状态推进都是条件 UPDATE，实际一部分是 FOR UPDATE 后 updateById。两种做法都有用途，注释应该准确反映实现。
- `succeeded()` 注释称清空 lastError，但实体字段使用默认更新策略，setLastError(null) 不保证数据库字段清空。当前展示按 state 判断，所以主要是注释与存储内容不一致。
- 状态常量已定义，但入口、恢复器和发布器仍重复写字符串；Redis key 前缀也分散拼接。统一复用现有常量即可，不需要再造框架。
- 部分通配符 import、单行 if 和嵌套三元表达式可以按团队格式统一。这些属于可维护性整理，优先级低于补偿缺口和重复 SQL。
- 完整注释可以保留，应集中解释业务规则、并发约束和异常语义；冗长或错误注释影响维护，不影响运行速度。

## 应当保留的设计

1. 申请记录先提交，再进行正式 Redis 预占，避免没有持久化受理依据的预占。
2. READY、CANCELLING 与终态分开；先提交终止裁决，再释放 Redis，最后更新 FAILED。
3. 消费、预占与终止通过同一申请行锁协调；扣数据库库存、写订单、更新成功状态处于同一事务。
4. 数据库一人一券唯一约束、stock>0 条件扣减，以及消费者幂等。
5. 消息发送未知时保留补发；同一申请使用稳定业务身份。
6. 默认不加载维护型集成测试；结果查询校验本人身份，orderId 以字符串提供给前端。
