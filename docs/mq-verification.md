## 实现与运行方式

采用“持久化申请表 + RocketMQ 普通消息 + 定期恢复 + 幂等补偿”。申请先持久化，再执行 Redis 预占；发送结果未知时保留申请供补发，不立即退款。消费事务将扣库存、写订单和成功状态一起提交，终止与消费通过同一申请行锁裁决。

- [设计与故障窗口](mq-design.md)
- [本机部署与显式数据库迁移](../deploy/rocketmq/README.md)
- 旧 Stream 消费循环、pending 处理和旧 `seckill.lua` 已移除，未保留两套运行模式。
- 数据库迁移重复执行通过；未清空旧库存、账号或订单。启动时校验申请表及订单唯一约束，缺失时明确拒绝启动。

## 真实接口、数据库与 MQ 验收

| 场景 | 结果 |
| --- | --- |
| 商户真实登录并发券，消费者经过 Nginx 抢购 | 返回字符串申请ID，最终查询成功并产生一笔订单 |
| 匿名抢购/查询、其他用户查询、商户身份访问消费者申请 | 拒绝访问，不暴露他人申请 |
| 对同一事件实际重复投递3次 | 订单、MySQL库存及Redis库存均只产生一次业务副作用 |
| 同一消费者重复抢同一张券 | 拒绝重复，不误退先前预占 |
| 10人并发抢3张券 | 恰好3单，数据库与Redis库存均为0；这是正确性验证，不是吞吐量压测 |
| 插单触发器注入故障 | 已扣MySQL库存随事务回滚；移除触发器后实际消费重试成功 |
| 实际消费重试耗尽并进入DLQ | 持久终止申请、释放本次预占，无订单；不是只调用死信处理方法的Mock测试 |
| 重复执行补偿与终止后的迟到预占 | 不多退库存，CLOSED申请不能重新预占 |
| Broker停止期间真实HTTP受理，随后终止并重启后端 | 申请保留，Broker恢复后补发并成功 |
| 已终止申请收到实际迟到消息 | 不复活订单 |
| 两个真实后端实例共同消费12笔消息 | 恰好12单，两实例均有实际消费记录，无重复扣库存 |
| 主消息、重试与死信队列核查 | 清理夹具前核实消息无积压和在途消费 |

另通过等价持久状态夹具验证四种恢复窗口：INIT已提交未预占、Lua已预占但数据库仍为INIT、READY未发送、释放已完成但数据库仍为CANCELLING。这些属于**恢复状态验证**，不声称在每条指令之间都实际终止过进程。
