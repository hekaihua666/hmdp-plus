## 1. 项目定位：保留能串成业务流程的功能

当前项目主线是：**发现门店 → 查看详情与探店笔记 → 参与优惠券抢购 → 查询异步处理结果**。

轻社交承担两件事：让门店有可阅读的内容，让消费者可以记住喜欢的作者。它不承担完整内容平台的粉丝推送、社交关系分析、私信和复杂评论系统。

因此，取舍标准不是“某章用了Redis就必须保留”，也不是“CRUD简单就全部删掉”，而是：

1. 是否支撑当前业务流程。
2. 是否与ES或其他模块重复承担同一种职责。
3. 保留后是否值得承担额外状态、同步、分页和失败处理成本。

发布笔记虽然主要是CRUD，但删除后，用户只能阅读预置数据，无法实际操作发布。相反，粉丝收件箱虽然有学习价值，却会把一次发布变成对许多收件箱的写入，需要额外考虑失败恢复和动态分页，所以从产品代码中移除了。

## 3. 两条主要流程

### 3.1 笔记与作者流程

```text
发布页上传照片、选择门店、填写正文
  → POST /blog
  → BlogServiceImpl.saveBlog
  → 校验输入、门店，构建允许写入的字段
  → MySQL保存笔记，返回笔记ID
  → 浏览器进入该笔记详情
  → 阅读者点赞、查看门店、进入作者主页或关注作者
  → 从“关注的作者”再次进入作者笔记
```

这条流程里没有“发布后遍历粉丝”，也没有“读取我的粉丝收件箱”。作者列表是找人的入口，首页和作者主页是找笔记的入口。

### 3.2 附近门店流程

```text
首页分类 / 底栏附近 / 搜索关键词
  → shop-list.html + shop-search.js
  → GET /shop/search（携带分类、坐标、半径、价格、评分、排序、页码）
  → ShopSearchServiceImpl构建ES查询
  → 同一响应返回list、total、aggregations
  → 页面同时更新商户列表与筛选面板统计
```

这里ES的搜索实现是原来已经存在的能力。本轮的关键是让原先仍走Redis GEO的纯分类列表也使用这套能力，并删除重复维护代码。

## 4. 第8章：笔记保留哪些，具体怎样改

### 4.1 发布为什么要重新构造Blog

看`BlogServiceImpl.saveBlog(Blog input)`。

Controller接收的JSON会绑定成Blog，但这个实体还包含id、userId、liked、comments、createTime等字段。浏览器正常表单没有这些字段，不代表直接调用接口的人不能提交。

如果直接执行`save(input)`，客户端提供的数据就可能进入原本应该由服务端控制的列。

现在执行的是：

```java
Blog blog = new Blog()
        .setUserId(UserHolder.getUser().getId())
        .setShopId(input.getShopId())
        .setTitle(input.getTitle().trim())
        .setContent(input.getContent().trim())
        .setImages(input.getImages())
        .setLiked(0)
        .setComments(0);
```

这段代码的设计含义如下：

- 作者身份取登录上下文，不相信JSON里的userId。
- 不复制输入id，避免把客户端选择的主键带入新增。
- 只复制标题、正文、图片地址、关联门店这些允许作者填写的内容。
- 点赞和评论从0开始；不复制客户端计数和时间。
- 时间仍按既有数据库/持久化规则产生，不把输入createTime当作真实发布时间。

发布前还检查必填、长度、图片地址串数量以及门店是否存在。这里对images是粗粒度的地址串校验，不能据此声称服务端已验证每张图的真实格式或所有权。

### 4.2 为什么保存后不再发给粉丝

原来保存成功后会：查询粉丝 → 遍历每位粉丝 → 向`feed:{粉丝ID}`执行ZADD。

现在保存成功就返回笔记ID。这个改动减少的不是一行API调用，而是整套收件箱状态：

1. 不再产生每个粉丝各一份的笔记引用。
2. 发布结果不再依赖遍历期间的Redis写入是否全部成功。
3. 不再需要Feed游标、同分时间戳偏移和收件箱翻页状态。

代价是：关注作者发新笔记后，不会主动出现在一个专属动态收件箱中。用户需要到首页或作者主页阅读。这是明确接受的产品取舍，不是假装保留了原来的关注动态。

### 4.3 笔记现在从哪读

| 入口 | 数据范围 | 身份要求 |
| --- | --- | --- |
| `/blog/hot?sort=hot` | 全站热门笔记 | 游客可读 |
| `/blog/hot?sort=latest` | 全站最新笔记 | 游客可读 |
| `/blog/of/shop?shopId=...` | 指定门店的笔记 | 游客可读 |
| `/blog/of/user?id=...` | 指定作者的笔记 | 游客可读 |
| `/blog/of/me` | 当前登录用户的笔记 | 需要消费者登录 |
| `/blog/{id}` | 单篇详情 | 游客可读 |

本人和作者笔记复用`queryBlogByUserId`。本人入口的userId由Controller取UserHolder，公开作者入口才接受要阅读的作者ID。

排序使用`create_time DESC, id DESC`。主键用于相同创建时间下的稳定顺序；这仍是页码分页，不等于有快照语义的游标分页。列表期间持续新增、修改或删除内容时，不能保证任何情况下都无重复/无漏读。

`isBlogLiked`除了判断点赞，还补充作者昵称和头像。游客没有UserHolder时返回isLike=false，因此公开阅读不需要先登录；写操作的认证仍由拦截器负责。

### 4.4 点赞怎样使用ZSet

```text
Key：blog:liked:{笔记ID}
member：点赞用户ID
score：点赞发生时的毫秒时间戳
```

它承担两个查询：ZSCORE判断某用户当前是否在集合中，倒序范围查询取得最近5位点赞者。

“最近点赞者”不是“用户热度排行榜”。score没有保存用户收到的总赞数。时间戳相同时，成员的顺序也不代表严格的点击先后。

### 4.5 为什么检查ZADD/ZREM返回值

考虑两个请求都先查到用户尚未点赞：

```text
请求A：ZSCORE为空 → ZADD实际新增 → 返回true → 数据库+1
请求B：ZSCORE为空 → ZADD发现member已存在 → 返回false → 不再+1
```

如果只依据第一次ZSCORE，而不看实际新增结果，两个请求可能把计数加两次。取消时同理，只有ZREM确实移除了成员，才减少计数。

`liked = liked + 1`由数据库执行原子加法；取消使用`GREATEST(liked - 1, 0)`避免减成负数。这里的负数保护不能修复所有历史差异，也不等于跨存储事务。

必须区分三件事：

1. **网页防连点**：一次操作结束前不反复发送请求。
2. **ZSet成员防重复及返回值判断**：处理多个请求落到同一新增/移除分支的情况。
3. **跨存储一致性**：Redis与MySQL之间失败、退出和混合操作的收敛问题。

当前只保留前两类的基础保护。Redis成功后MySQL失败仍可能出现差异，接口本身又是toggle：顺序调用两次，会先点赞再取消。不能把请求任意重放、消息幂等和强一致等概念混在一起。

### 4.6 最近点赞者为什么还要ORDER BY FIELD

Redis返回的是排好序的用户ID。SQL的`WHERE id IN (...)`只保证属于这个集合，不保证按ID参数顺序返回。

所以代码用`ORDER BY FIELD(id, ...)`恢复Redis给出的顺序，然后转换成只包含公开字段的UserDTO。

拼接的ID先经过Long解析，不是把HTTP参数原样拼进SQL。头像条无需读取或向客户端返回手机号。

## 5. 第9章：关注如何精简，以及本轮发现的快照漏洞

### 5.1 保留关系，不保留粉丝动态系统

原来关注关系同时存在tb_follow和Redis Set中，发布又使用粉丝关系推送Feed。

现在：写关注、查关注、列出作者，统一以tb_follow为准。Redis关注Set、共同关注和Feed收件箱都没有新的读写路径。

保留的接口是：

```text
PUT /follow/{作者ID}/true     确保关注
PUT /follow/{作者ID}/false    确保取关
GET /follow/or/not/{作者ID}   当前用户是否关注
GET /follow/of/me?current=1   本人关注的作者列表
```

关注接口表示目标状态，不是“调用一次就反转一次”。如果本来已经关注，重复true应保持关注；如果已经取关，重复false应保持不存在。

### 5.2 为什么“查不到就插入”有竞争

```text
A：COUNT=0
B：COUNT=0
A：INSERT
B：INSERT
```

没有唯一约束或有效串行化时，两次检查都可能正确地看见0，然后各插一行。

这里选用当前用户的主键行作为锁定点：

```java
User current = userService.query()
        .eq("id", userId)
        .last("FOR UPDATE")
        .one();
```

选择这行而不是尚不存在的关注记录，是因为登录用户已经存在，有确定的主键行可锁。同行为主体的请求会等待同一行，数据库实例上的锁也会约束多个应用进程。一次用户的关注操作量不大，这样比再维护一套Redis关系锁更直接。

代价是同一用户对不同作者的关注修改也会串行，而且可能与修改该用户行的其他事务竞争。这不是为社交平台大规模写入专门设计的方案。

### 5.3 只有FOR UPDATE还不够：普通SELECT不能提前

补写注释时复核发现，上一版顺序是：

```text
查询作者是否存在（普通SELECT）
  → 锁当前用户行（SELECT ... FOR UPDATE）
  → COUNT关注关系
  → 需要时INSERT
```

本机实测隔离级别为`REPEATABLE-READ`。InnoDB在该级别下，普通一致性读使用事务中首次此类读取建立的快照；锁定读读取较新的行，但不会自动刷新已经建立的普通读取快照。参见[MySQL 8.0一致性读说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)与[锁定读说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。

因此可能发生：

| 顺序 | 请求A | 请求B |
| --- | --- | --- |
| 1 | 普通查询作者，建立快照S1 | 普通查询作者，建立快照S2 |
| 2 | 获得当前用户行锁 | 等待同一用户行锁 |
| 3 | COUNT=0，插入并提交 | 继续等待 |
| 4 | 已提交 | 获得用户行锁 |
| 5 | — | COUNT仍用旧快照S2，看不见A刚提交的关注 |
| 6 | — | 再插入一行 |

这就是“执行已经串行，但读到的仍是旧数据”。不能仅看见`@Transactional`和`FOR UPDATE`就断言整个方案正确。

### 5.4 现在怎样修

当前方法改为：

```text
只做不访问数据库的参数判断
  → 首次数据库访问就锁当前用户行
  → 检查当前用户是否存在
  → 普通查询作者是否存在
  → COUNT当前用户与该作者的关系
  → 按目标状态保存或移除
  → 事务提交/回滚，释放锁
```

关键不是“多加一把锁”，而是把普通查询放到锁之后。当前HTTP路径通过Spring代理开启本方法事务，锁前的登录身份来自Redis会话，没有提前执行数据库快照读。

这样B获得锁以后才第一次建立普通读快照，就能看到A在释放锁前提交的关注关系。

注释明确写出了两个前提：

- `@Transactional`要通过Spring代理生效，锁必须覆盖检查和写入，不能查完立刻释放。
- 如果将来从已有数据库快照的外层事务调用本方法，必须重新审视快照前提，不能只照搬当前顺序论证。

此外，这里没有新增tb_follow唯一索引。它约束的是遵循当前服务流程的写入者，绕过服务直接写表不受保护。数据库唯一约束是另一种兜底选择，但本轮不为注释任务增加数据清洗和结构迁移。

### 5.5 为什么上一轮测试没发现

上一轮先通过页面完成一次关注，再并发重复true，能证明“关系已存在时不重复新增”，但不能证明“关系原本不存在时，首次并发关注也正确”。

本轮新增了更严格的真实测试：

1. 创建本批临时消费者与作者，确认尚无关系。
2. 用独立数据库事务先锁住消费者行。
3. 同时启动六个真实HTTP关注请求，让它们等待同一行锁。
4. 释放屏障，观察最终关系行数。

修复前已实测六个请求均成功，却插入六条关系。修复后在相同屏障场景下，六个请求同样全部成功，最终只有一条关系。Mock调用顺序测试不能代替这类真实InnoDB行为验证，结果和证据文件见第14节。

### 5.6 取关与本人列表

取关条件同时包含user_id与follow_user_id，只删除“我对这位作者”的关系。如果旧数据重复，移除所有对应行，不会误删其他人的关注。

列表SQL为：

```sql
SELECT u.id, u.nick_name AS nickName, u.icon
FROM tb_user u
WHERE EXISTS (
    SELECT 1
    FROM tb_follow f
    WHERE f.user_id = :currentUserId
      AND f.follow_user_id = u.id
)
ORDER BY u.id DESC
LIMIT :offset, 10;
```

这段SQL有三个设计点：

- 用EXISTS判断是否存在关系，不把历史重复关系展开成重复作者。
- 只返回ID、昵称、头像，不加载手机号等不需要的数据。
- 按作者ID倒序，每页10人；不是按最近关注时间排序，也不是粉丝动态Feed。

currentUserId来自UserHolder，不由浏览器选择。`#{...}`是MyBatis参数绑定，不是把原始字符串拼进SQL。

## 6. 第10章：为什么附近商户改为统一ES

### 6.1 原来存在两条链

```text
纯分类：Redis GEO取ID/距离 → MySQL回表 → 返回列表
组合搜索：ES过滤/排序/高亮 → 返回列表/聚合
分类统计：另外再向ES请求一份统计
```

两条链需要分别维护分类、坐标、排序、分页和失败状态。分类列表与统计还可能来自不同响应、不同更新时刻，增加解释和排查成本。

项目已经有ES的geo_point、半径过滤、距离排序和聚合，因此继续维护Redis GEO不能给当前产品带来相应收益。

### 6.2 这次真正改动的位置

1. `shop-search.js`删除isEsSearch分支和单独queryStatistics请求，列表统一调用`/shop/search`。
2. 删除ShopServiceImpl.queryShopByType、IShopService对应方法和`/shop/of/type`入口。
3. 删除ShopGeoInitializer，启动时不再导入Redis GEO。
4. ShopChangedEvent不再带previousTypeId。
5. 商户变更监听器不再删除旧分类GEO成员、添加新分类坐标。
6. 演示数据脚本不再geoadd，但仍保留其既有秒杀库存初始化规则。

原有ES搜索实现继续复用，没有为“附近”重新建立第二份索引或把整个查询模块重写一遍。

### 6.3 坐标、半径、排序分别表示什么

| 参数 | 含义 | 示例 |
| --- | --- | --- |
| x | 经度 | 120.149993 |
| y | 纬度 | 30.334229 |
| radius | 限定范围，单位米；空表示不限半径 | 5000 |
| sort=distance | 在满足全部过滤条件后按距离排序 | 最近优先 |

按距离排序不自动意味着5公里内；5公里筛选也不强迫按距离排序。排序和范围是独立维度。

当前参考坐标仍固定在杭州，没有接设备GPS。代码和页面都避免把它描述为已获取设备真实位置。

普通分类默认最近排序、不隐藏半径限制；底栏“附近”则显式携带`sort=distance&radius=5000`。这一变化也让分类中较远的商户不再被旧GEO分支静默排除。

### 6.4 为什么一次响应就能更新统计

返回值的相关字段为：

```text
list                 当前页商户
total                当前全部过滤条件下的商户总数
aggregations
  priceAgg           价格区间桶
  scoreAgg           评分区间桶
  distanceAgg        距离累计范围桶
```

`applyAggregations`把桶转换为label到count的字典，模板与后端定义的同名筛选选项对应。

两点容易误读：

- 1公里、3公里、5公里是重叠的累计范围，不能把数量相加当作总数。
- 当前聚合包含当前筛选条件。如果已经限定5公里，10公里桶也只统计这批当前结果，数量可能与5公里相同。它不是“点击10公里以后预计有多少商户”的排除本维度式Facet统计。

没有桶、接口失败和真的0家是不同状态。代码用aggState区分loading/ready/error，缺失的桶显示不可用，不把错误当作0。

### 6.5 快速切换条件，为什么旧响应不会盖住新结果

假设先选择美食，马上又选择亲子游乐。美食请求可能更慢，在亲子请求之后返回。

`resetAndSearch`会增加version；每次请求记住自己的version。then、catch、finally写状态前都检查它仍等于当前version。

这不仅防止旧列表覆盖新列表，还防止旧finally把新请求的loading误设为false。页码只在成功后增加，因此失败重试仍是原来的页，不会跳页。

### 6.6 为什么仍保留/shop/of/name

发布笔记需要选择一家真实门店，这个接口只承担简单的名称筛选和固定分页，不提供半径、聚合或附近列表。

因此“附近搜索统一ES”并不要求删除一切MySQL查询。写前存在性检查、详情缓存回源、后台归属编辑也仍使用MySQL。

## 7. 店铺变更后，缓存和ES现在怎样更新

### 7.1 事件变轻了

以前previousTypeId供监听器移除旧GEO分类成员。GEO退役后，下游不再需要这个字段，ShopChangedEvent只保留shopId。

监听器按ID重读最新资料，再更新ES中的名称、分类、坐标等字段。这里是应用内事件，不是已经持久化的MQ消息。

### 7.2 详情缓存失效：提交后、同步尝试

`updateRedisAfterCommit`订阅AFTER_COMMIT，删除`cache:shop:{id}`。新增也要失效缓存，因为此前有人可能查询过尚不存在的ID，留下缓存空值。

不在事务提交前删除，是为了避免其他请求在提交前从数据库读到旧值又回填旧缓存。

方法没有@Async，正常路径会在写请求返回前尝试删除缓存；这不是“绝不出现旧缓存”的强一致承诺。数据库已经提交时，Redis异常也不能把原事务重新回滚。

### 7.3 ES：提交后、异步同步

另一个监听器有@Async，调用既有syncById。这样不把ES网络延迟放在主写操作的同步链中，但应用内异步事件没有持久重投，异常只记录日志。

两个监听器独立处理，Redis删除失败不会直接阻止ES同步；反过来ES失败也不会撤销已提交的数据库。

订单MQ已有持久化申请和恢复任务，店铺ES事件没有这套保证。二者必须分开讲，不能因为项目接入了RocketMQ，就把所有异步操作都描述成可靠投递。

## 8. 页面怎样配合后端收敛

### 8.1 共用个人页与作者页

info.html与other-info.html共用profile.js/profile.css。isOwn决定页面展示与接口选择，但它不负责授权。

| 模式 | 资料来源 | 列表 |
| --- | --- | --- |
| 我的主页 | `/user/me` | 我的笔记、本人关注作者 |
| 作者主页 | `/user/{id}`及公开简介 | 该作者公开笔记 |

游客访问“我的”会去登录；访问作者主页可以直接看笔记，不先调用受保护的/user/me。

blogs/authors、notePage/authorPage和两个结束标记各自独立。成功才推进下一页，失败可重试；用户资料尚未加载时重试整个页面，列表失败则只重试当前页。

### 8.2 取关以后为什么重载第一页

如果第一页有10人，删掉其中1人，原第11人会前移。如果仅删除当前卡片，再继续用offset=10，可能跳过前移的人。

所以当前流程取关成功后重置作者列表、页码与结束标记，再请求首页。它处理的是当前页面删除记录后的偏移问题，不保证其他客户端持续修改时拥有完整快照语义。

### 8.3 发布和上传怎样衔接

发布页的submitting阻止提交期间重复点击，uploading阻止照片地址未返回就发布。FormData的multipart boundary由浏览器生成，不手写一个与请求体不同的边界。

上传接口先返回`/blogs/...`，页面补`/imgs`得到Nginx静态地址，再把地址串放进发布请求。

这里“上传文件”和“保存笔记”不是一个事务。取消草稿或移除照片只影响草稿引用，可能留下未引用图片；当前没有文件所有权表和孤立文件清理任务。

旧的按公开文件路径删除服务器图片接口已移除。前端图片类型与9图限制是体验校验，不应被表述为完整的服务端文件安全校验。

### 8.4 点赞与正文展示

详情点赞操作等待服务端完成后重新查询笔记和最近点赞者，不用本地自增猜结果。liking/followingBusy用于防连点，不能替代后端并发控制。

正文使用v-text展示，兼容课程旧数据中的换行标签。不再把作者输入直接交给v-html执行；这是纯文本策略，不是完整富文本编辑器或通用HTML清洗器。

### 8.5 为什么长列表不会被底栏挡住

profile.css把页面做成纵向flex：页头、可滚动正文、真实占位的底栏。

- 正文`flex:1; min-height:0; overflow-y:auto`：允许内容区收缩，并只在正文滚动。
- 底栏改为static并占68px：覆盖原绝对定位，避免盖住最后一条卡片。
- 桌面三列、窄屏两列：卡片宽度使用minmax(0,1fr)，长标题能够换行。

空态、加载态、失败态分开展示，网络失败不会被写成“作者还没有笔记”。

## 9. 登录边界与公开字段

WebMvcConfig仍先执行RefreshTokenInterceptor识别可选会话，再由LoginInterceptor保护必要操作。

公开白名单精确到相关路径，不直接放开`/blog/**`或`/user/**`。数字ID规则避免把/user/me等私有入口一并匹配进去。

| 操作 | 游客 | 消费者登录后 |
| --- | --- | --- |
| 门店/首页/作者笔记、详情、最近点赞者 | 可读 | 可读，并可显示本人点赞状态 |
| 作者昵称、头像、城市、简介 | 可读字段白名单 | 同样不返回不必要字段 |
| 发布、上传、点赞、关注、本人列表、退出 | 拒绝或页面引导登录 | 按本人身份处理 |

UserController.queryUserById返回UserDTO；queryUserInfo显式选择userId、city、introduce，不直接返回带生日、积分、会员字段的UserInfo实体。

消费者退出只撤销当前请求的`login:token:`会话，不删除所有设备会话，也不碰商户/管理员命名空间。前端finally清本地状态；网络失败时，本地退出不意味着服务端一定已撤销。

清除hmdp_seckill_pending只清浏览器里的查询快捷信息，不取消数据库中已经受理的抢购。
